# 动机、任务、目的与现状分析
现有agent benchmark在制作时，没有考虑到工具调用结果返回时可能存在的噪声，默认都是调用成功且返回信息无误的。

为了研究agent/LLM 在面对有噪声的工具时的性能，我们想要构造这样一个benchmark。

初步实验验证：
找一个agent项目，它能够通过调用工具来解决问题。
比如我们这里的Search-R1(https://github.com/PeterGriffinJin/Search-R1)，它通过调用搜索引擎查找资料回答QA问题（HotpotQA, 2WikiMultiHopQA）。

那么初步实验验证很简单：
这里的agent只有一个工具，就是search（通过LLM在输出过程中输出<search>content to be searched written in natural language</search>，来触发search工具）。宏观上来讲，我们现在的任务很简单：就是要给search工具调用之后的结果进行加噪处理再返回给模型，使得模型的表现降低，从而证明我们的猜想，体现我们的benchmark的价值。

加噪可以通过一个额外的LLM，在prompt的指导下，对工具调用的结果进行加噪处理。

经过商讨，我们初步定义了五大类在现实使用场景中真的有可能出现的噪音类型，且保证类型间不会有overlap。
五种类型：失败，不完整，错误，冗余，诱导。

# 新加运行参数（这一部分也是重中之重，必须合理）
为了能够添加噪声，我们需要新加一个module，专门用来添加噪声，因此我们就在源代码的基础上，添加一些与加噪有关的运行参数。我这里初步考虑可能需要加两大类运行参数：1. 一些通用的运行参数（不区分五种噪声中的哪一种），2. 同时也要给不同的噪声设置一些专门的运行参数（每种噪音客制化的参数）

## 加噪相关的运行参数（通用）
--noise_category：要加噪的类型，可选[failure(default), incomplete, error(wrong), redundancy,induce]。现在只是用户测试的时候只能选择一种噪声，后续可以改代码，让用户能够能够直接传入一个list，包含好几种噪声，然后通过程序，自动化判断在哪一步、添加什么类型的噪声。
--noise_prob_per_episode：每一个episode的被加噪的概率
--noise_nums_per_trail：每一个trail的最大加噪数量（注意：1. 这能够在一定程度上反应这条测试数据的难度，显然，加噪次数越多，难度越大，我们可以把难度的控制权交给用户。2. 这个值是“最大加噪数”，但不意味着在一条trail中一定会达到。考虑以下情况：① noise_prob_per_episode比较小，每一步都没能加噪/极少步被加噪，一直到问题解决。因此可以设置，加噪概率=1，设置从哪一步开始加噪。比如设置加噪概率为1，从第5步开始，最大加5次，那么可保证从第5步开始，往后加5次。② 问题本身就比较简单，比如一个问题，本身只需要调用工具一次，那）

--是否设置每一种tool在整个trail中只能被加噪一次

# 通过加五种类型噪声，如何使得模型的性能下降。
为了使得所加上的噪声能够有效，我们必须进行深入的分析。

比如：对于“失败”这种类型，我们很容易的想到，加噪的方法可以是在调用serch之后，给它返回403，404。但是模型在收到结果之后，可以一直请求一直请求，直到请求成功为止呀，这如何能够让模型的表现下降？显然，在“给模型返回403，404...”和“模型表现下降”中间缺少了一些重要的处理环节，这些细节是我们需要仔细考虑的。
